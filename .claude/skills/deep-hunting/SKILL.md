# Deep hunting

## Owner and input

The orchestrator may run this skill inline or assign one canonical surface to one `deep-hunt-agent`. Never give two owners the same surface or output path. Consume its exact `surface-inventory.md` rows, surface record, scope rule, decision fingerprint, value flow and enforcement point, normal seed or grounded dependency edge, coverage axes, evidence provenance/deployment confidence, executable hunt seeds, fixtures, prior tests and limits. Return one `work_status`: `continue`, `surface-tested-bounded`, or `blocked`; return candidate proposals, `fixture-needed`, `reopen-recon`, and `reopen-extraction` separately as zero or more handoffs. Only the orchestrator changes shared queues and the interaction inventory.

If the surface, attacker, protected value/state, enforcement point, boundary, invariant, valid control, or oracle is not grounded, emit the exact recon or extraction handoff. If only an owned fixture is missing, emit `fixture-needed`; the scheduler resolves it with `identity-signup` and resumes this surface. Keep `work_status: continue` while any independent or autonomously unlockable work remains. Do not invent target behavior.

## Per-surface loop

1. Consume and maintain the complete engagement WSTG catalog/delta ledger defined in `hunting-prompts.md`. Map every exact case assigned to this surface across its material axes, then add architecture-specific `TARGET-SPECIFIC` objectives and relevant current control/mechanism standards. These define coverage outcomes, not a mandatory sequence or technique. Record exact id/version, why it applies, and the evidence that closes each objective/axis; broad categories, missing ids and recon-path results are not terminal substitutes. `not-applicable` requires positive evidence; lack of visibility is `unresolved`; an unavailable operator-only prerequisite is `blocked`.
2. Turn applicable objectives and architecture-specific risks into explicit hypotheses. For each open hypothesis, compare plausible evidence paths and experiments by credible impact, attacker reachability, expected severity-changing information gain, confidence, cost, operational risk and ability to falsify alternate causes. Select the dominant next action, record why and its pivot condition, and prevent starvation of the remaining axes.
3. Start from the strongest semantics-preserving seed: observed transaction, normal browser/dependency flow, exact source/schema path, recovered implementation evidence or a hybrid. Source may establish logic and focus the test, but a live consequence requires deployment binding and runtime proof. Run the smallest decisive experiment with positive, boundary-respecting negative and applicable alternate-cause controls. Preserve coupled semantics unless the hypothesis changes them.
4. Use targeted request, value, state, role, tenant, channel, parser, timing, or concurrency variation only when the WSTG objective or target model calls for it. Compare complete response/message, browser behavior, durable before/after state, and downstream effects; a status code or scanner verdict is not a conclusion.
5. Minimize a signal, interleave controls, repeat with clean state in proportion to noise and consequence, and rule out WAF/gateway, cache/CDN, normalization, stale state, retry, client-only effects, rate limits, and jitter. Build the shortest controlled evidence ladder to the highest credible scoped consequence without crossing `CLAUDE.md` ceilings.
6. Emit handoffs immediately: a new scoped host/service to recon; new code, identity, operation, role/state, message, parser, consumer, service, trust edge or channel to extraction; a reproducible material failed-boundary premise to the candidate queue. A handoff never closes the test or surface; every candidate requires independent validation.
7. Preserve demonstrated narrow primitives and their feasible chain prerequisites. Attempt a compound path only when every edge is evidence-backed; never inherit reachability, impact or severity from a speculative link. Continue independent hypotheses after a chain fails.
8. When the current queue appears exhausted, run a fresh hypothesis-synthesis pass from the latest graph, WSTG/mechanism ledger, results, alternate evidence paths and demonstrated primitives. Challenge uncovered axis combinations, enforcement differentials, producer/consumer edges, alternate roles/states/channels/parsers and feasible chains without inventing target behavior. Queue every hypothesis that meets the kernel's eligibility test and repeat after any material discovery; reach hypothesis fixed point only when a complete pass produces no new eligible item.
9. Give every applicable objective/axis one result: `tested-bounded`, `candidate`, evidence-backed `not-applicable`, `dedup`, or `blocked`, with evidence and exact reopen condition. Use `work_status: blocked` only when every remaining item depends on an operator-only prerequisite; use `surface-tested-bounded` only when every applicable axis and evidence-grounded severity-changing hypothesis is resolved, the final synthesis pass has no delta, and no handoff or prerequisite remains open.

## Tool selection

- Choose tools by the security semantics that must be preserved, not by a fixed preference. Use headless `playwright` when origin, client execution, browser state, navigation or multi-user context matters; use source/schema inspection or the smallest protocol client when it yields stronger evidence without losing those semantics. Use headed mode only for unavoidable operator interaction or a recorded headless limitation.
- If no available tool can preserve secrets or protocol state, keep the test in the capable context or mark only that path blocked.
- Start `interactsh-client -json -o <artifact>` before a justified blind/outbound test and use a fresh marker per case; a callback proves outbound reachability only.
- Use `sqlmap` only after a manual differential identifies a specific injectable parameter/parser. Limit technique, level, risk, and proof; never crawl, dump data, or request a shell.
Record tool/version, material options, fixture labels, exact action/request ids, timestamps, raw redacted evidence, and cleanup. Keep secrets tool-managed.

## Record and return

Append one row per test to `engagements/<name>/knowledge-base/tests/<surface>.md`: id, surface, versioned objective/reference or target-specific hypothesis, coverage axes, applicability state, evidence options and chosen strategy, attacker/preconditions, invariant, seed/variation, controls/oracle, observation, alternate causes, bounded conclusion/status, evidence, demonstrated primitive/impact rung, feasible chain edges, cleanup, pivot and reopen condition. Store every target-derived input, output, capture and retained scratch under `engagements/<name>/knowledge-base/artifacts/`; ingest and clear unavoidable tool spill before continuing or returning. Propose a candidate file only at the candidate gate.

Return surface/assignment id; standards/applicability matrix; axis results; target-specific hypotheses/results; final synthesis inputs and delta; evidence and cleanup; primitives/chain edges; candidate, fixture, recon and extraction handoffs; remaining executable tests; blockers/reopen conditions; and exactly one `work_status` with rationale. Never self-validate, assign final severity/reportability, or claim safety beyond the tested boundary and axes.
